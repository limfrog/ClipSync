# 0.4.3 기기 발견·재연결 검증

## 변경

0.4.0은 같은 공유기의 기기도 공개 DHT로 찾아야 했습니다. 0.4.3는 LAN 멀티캐스트 발견과 직접 TCP 연결을 추가하고, 기존 DHT/Noise 경로와 병행합니다. 모든 PC가 같은 역할이며 별도 서버 배포는 없습니다.

LAN 광고에는 불투명 그룹 식별자·기기 ID·일시 TCP 포트·HMAC만 넣습니다. 비밀번호·연결 키·클립보드는 광고하지 않습니다. HMAC가 맞는 광고의 실제 발신 IP에만 연결하며, 수신 연결도 양쪽 난수·기기 ID·공개 키에 묶인 비밀번호 증명을 통과해야 합니다. 클립보드 내용과 파일 조각은 기존 AES-GCM 암호화를 유지합니다. WAN의 Noise 핸드셰이크와 유료 중계 비활성화도 유지합니다.

LAN 광고는 1초 주기이고 새 기기를 보면 응답합니다. 어댑터별 송신 완료 후 다음 어댑터로 넘어가, 비동기 주소 조회 중 마지막 어댑터로 모든 광고가 몰리는 문제를 막습니다. 동시 TCP 연결은 기기 ID로 한쪽만 시작하며, LAN/Noise 중복 경로는 양쪽에서 동일한 순위로 정리합니다. 인증 대기 8초, 대기 소켓 수 48개, 최대 상대 기기 15개, 송신 대기 버퍼와 프레임 크기를 제한합니다. 5초 간격 연결 응답 확인과 15초 무응답 기준으로 끊어진 LAN 경로를 정리합니다.

인증된 공개 키 최대 15개와 DHT 노드 최대 16개를 `connection.enc`의 기존 운영체제 암호화 저장에 포함합니다. 공개 키 직접 접속과 그룹 탐색을 동시에 시작하고, 첫 30초는 5초마다 탐색을 갱신하며 이후 30초 간격으로 낮춥니다. 진행 중인 탐색 갱신은 라이브러리가 합칩니다. `다시 찾기`는 2초 이내 중복 요청을 제한합니다. 저장/삭제는 같은 큐를 사용하고 세션 ID를 확인해 이전 세션 정보가 새 그룹에 저장되지 않도록 합니다.

## 실제 검증 범위

테스트는 동일한 Linux 호스트의 독립 세션·실제 UDP/TCP 소켓으로 수행했습니다. 아래 수치는 서로 다른 실물 PC 또는 실제 WAN의 측정값이 아닙니다.

- 인터넷 탐색 노드 없이 3개 세션 연결: 25~42ms. 같은 조건의 기기 재시작 후 복귀: 12~29ms. 고정된 약속 시간이나 WAN 성능을 의미하지 않습니다.
- 같은 탐색 주제를 강제로 사용하더라도 다른 비밀번호의 광고·연결이 거부되며 클립보드를 받지 않습니다.
- 한 기기 종료 시 남은 두 기기는 계속 동기화하고, 저장된 ID/seed로 복귀하면 다시 연결됩니다. 여러 광고 주기를 지난 뒤에도 연결 수가 중복 증가하지 않습니다.
- 실제 격리 DHT에서 LAN을 끄고 기존 기기를 기억한 뒤 재시작합니다. 새 세션의 그룹 탐색 주제를 고의로 바꿔 그룹 검색이 불가능한 조건에서도 기억한 공개 키로 접속하고 텍스트를 받았습니다(재접속 관찰 약 11ms). 실제 WAN NAT 통과를 재현한 테스트는 아닙니다.
- 운영체제 보안 저장 어댑터를 통해 기기/노드 캐시를 암호화 저장·복원하고, 저장소가 없을 때 평문 저장을 거부하며, 연결 해제 시 파일을 삭제합니다.
- 실제 Electron UI의 검색·고정·설정·숨김 후 동기화와 Linux Secret Service를 이용한 저장·재실행 복원·연결 해제 후 삭제를 통과했습니다.

일반 자동 검사 37개를 통과했습니다. 어댑터별 송신 수정 후 [macOS arm64 자동 검사](https://github.com/limfrog/ClipSync/actions/runs/39479787073/job/118825028614)와 [Windows 자동 검사](https://github.com/limfrog/ClipSync/actions/runs/39479787073/job/118825028434)도 성공했습니다. 각각 같은 OS 호스트 안에서 수행한 검사이며, 서로 다른 Mac–Windows 실물 연결 성공을 의미하지 않습니다.

공개 DHT 접근은 이 클라우드에서 제한되므로 외부망의 실제 연결 성공·지연 개선을 검증했다고 주장하지 않습니다. 기본 탐색망에 도달하지 못하는 경우와 NAT가 직접 연결을 막는 경우에는 재시도 간격만 줄여도 해결되지 않습니다. Windows/macOS의 방화벽 허용 및 실제 설치 후 기기 간 동작도 별도 실기기 확인이 필요합니다.

패키지 앱 두 개의 독립 클립보드 검사는 12개 시나리오(상위 테스트 포함 13개)를 통과했습니다. 외부 DHT가 없는 조건에서 양쪽 LAN 경로를 확인하고, 텍스트·이미지 픽셀·한글 프로그램·500,000,000바이트 파일의 SHA-256과 파일명을 검증했습니다. 전체 약 38초, 500MB 파일 생성·전송·검증 시나리오 약 14.8초였습니다. 결과/실행 파일·ASAR 해시는 `test-results/pair-report.json`에 기록합니다.

Mac의 기본·교차 패키징 경로 모두 `NSLocalNetworkUsageDescription`을 포함하며, 네이티브 macOS 릴리스 작업에서 Info.plist 키를 확인합니다. 이는 권한을 자동 승인하거나 실제 Mac–Windows 연결을 확인한 것을 의미하지 않습니다.

## 실물 Mac–Windows 확인

[같은 공유기에서 두 실물 기기를 확인하는 절차](physical-verification.md)를 별도로 준비했습니다. **연결 상태 복사**는 버전·OS/CPU·탐색/연결 수·오류 코드만 담고, 키·비밀번호·IP·기기 이름·클립보드 내용은 제외합니다. 이 보고서는 기록하거나 상대 PC에 자동 전송하지 않습니다.

## 재실행

```sh
npm run build
npm test
npm run test:desktop
npm run test:persistence
npm run package
npm run test:pair
```

`tests/group.test.ts`는 LAN을 끈 실제 DHT 경로를 검사합니다. `tests/lan.test.ts`는 DHT 노드를 주지 않는 조건을 검사합니다. `test:pair`는 서로 다른 X 디스플레이와 프로필의 패키지 앱 두 개에서 외부 DHT를 사용할 수 없게 하고, 양쪽의 실제 선택 경로가 LAN인지 확인합니다. 일반 사용자 환경에서는 공개 DHT 탐색을 병행합니다.
