# 수신 파일 중복 저장 검토

2026-10-21 (Asia/Seoul). 코드 검토 결과이며, 이 문서의 중복 수신 방지 기능은 0.4.5에 구현되지 않았습니다.

## 결론

파일명·크기로 후보를 좁히고 SHA-256까지 같은 파일은 기존 수신 파일을 재사용하는 방식으로 개선하는 것을 권장합니다. 새 클립보드 이벤트는 처리하되 파일 데이터 재전송과 중복 파일 생성만 생략해야 합니다. 반복 복사와 파일 클립보드 기록 재사용이 많은 이 앱에 적합합니다.

## 현재 코드에서 확인한 동작

- `TransferManager.offer()`는 파일 전체 SHA-256을 계산한 다음, 데이터 전송 전에 이름·크기·SHA-256을 `offer`로 보냅니다. 비교에 필요한 송신 측 해시가 이미 있습니다.
- `MediaSync.accept()`는 기존 수신 파일을 비교하지 않고 항상 새 전송을 수락합니다.
- `TransferManager.publish()`는 같은 이름이 있으면 `(1)`, `(2)`를 붙입니다. 원본 덮어쓰기를 방지하지만 동일 내용도 새 파일로 저장합니다.
- 수신 중 SHA-256 검사는 손상을 확인하기 위한 것입니다. 기존 파일을 재사용하는 검사는 현재 없습니다.
- 클립보드 반복 감지는 최근 지문과 전송 ID를 사용합니다. 파일 기록을 다시 복사하면 새 전송 ID가 생기므로 영구적인 내용 중복 방지가 되지 않습니다. 사용자 환경에서 발생한 모든 반복의 원인이 이 경로라고 단정한 것은 아닙니다.

## 안전한 처리 기준

| 조건 | 처리 |
| --- | --- |
| 같은 이름의 후보가 없음 | 기존처럼 수신 |
| 이름은 같고 크기가 다름 | 별도 파일로 수신, 기존 파일 보존 |
| 이름·크기·SHA-256 일치 | 기존 파일 경로 재사용, 본문 전송 생략, 클립보드 갱신 |
| 이름·크기는 같고 SHA-256 다름 | 별도 파일로 수신, 기존 파일 보존 |
| 파일 삭제·읽기 실패·검사 중 변경·불완전 파일 | 재사용하지 않고 수신으로 전환 |

한글 파일명은 현재처럼 NFC로 정규화하고, 대소문자 충돌은 실제 파일 시스템 특성을 따라야 합니다. 이미 번호가 붙은 파일도 찾을 수 있도록 원래 이름·크기·해시와 실제 저장 경로를 연결한 수신 기록이 유용합니다. 최초 구현에서 이름과 크기를 곧바로 동일성의 증거로 사용하면 안 됩니다.

## 속도와 안정성

비교 비용은 수신 PC에서 후보 파일을 한 번 읽고 SHA-256을 계산하는 비용입니다. 매번 받으면 송신 PC의 파일 읽기·네트워크 전송·수신 PC 저장과 해시 검사를 다시 수행합니다. 큰 파일·외부 네트워크·반복 복사에서는 재사용의 이점이 큽니다. 아주 작은 파일, 느린 수신 디스크와 빠른 내부망 조합에서는 비교가 더 빠르다고 보장할 수 없습니다. 그래도 중복 저장·디스크 쓰기·네트워크 사용을 줄이는 효과는 있습니다. 기기별 실제 소요 시간은 구현 후 측정해야 합니다.

폴더 전체의 모든 파일을 매번 해시하지 않고, 이름·크기와 수신 기록으로 후보를 좁혀야 합니다. 수정 시간은 후보 선별과 변경 감지에 사용할 수 있지만 내용 일치의 최종 증거가 아닙니다. 외부에서 변경 가능한 파일의 예전 해시를 크기·수정 시간만 보고 무조건 신뢰하면 손상된 파일을 재사용할 수 있습니다. 검사 전후 파일 상태와 재사용 시점의 유효성을 확인해야 합니다.

## 구현 시 필요한 검증

재사용 완료를 송신 측에 알리는 프로토콜 처리가 필요합니다. 현재 송신 측은 전체 전송을 마친 뒤에만 `done`을 허용하므로 수신 전에 단순히 `done`을 보내면 오류가 됩니다. 재사용 지원을 서로 확인하고 구버전 상대에게는 기존 전송으로 돌아가는 호환 동작을 설계해야 합니다.

이름·크기가 같지만 내용이 다른 파일, 같은 파일의 반복 복사, 번호가 붙은 기존 파일, 한글 NFC/NFD, 재시작 이후 재사용, 삭제·수정·손상·심볼릭 링크, 두 기기의 동시 수신, 전송 중 취소·연결 해제, 여러 파일 묶음과 최신 클립보드 우선 적용을 검증해야 합니다. 새 파일 저장의 기존 해시 검사와 덮어쓰기 방지는 유지해야 합니다.

현재 창 이동·아이콘 수정과 구분되는 전송 프로토콜 변경이므로 별도 기능 변경으로 다루는 것이 적절합니다.
